# 04 — Non-Functional Requirements

## الأداء (Performance)

- زمن استجابة توليد تقرير جديد (Cold, غير مخزَّن مسبقًا): هدف ≤ 8 ثوانٍ حتى ظهور أول بيانات (Progressive rendering مقبول: عرض معلومات الحساب فورًا، ثم تحميل تحليل AI تدريجيًا).
- تقرير مخزَّن مسبقًا (نفس اليوزر خلال آخر ساعة مثلاً): ≤ 1 ثانية (من Cache).
- زمن استجابة API الداخلي (P95): ≤ 500ms لأي Endpoint لا يتضمن استدعاء مزود خارجي.
- لوحة CRM/Admin يجب أن تدعم عرض جداول بآلاف السجلات بدون تجميد الواجهة (Pagination/Virtualization إلزامي).

## قابلية التوسع (Scalability)

- محرك جمع البيانات (`10_TIKTOK_DATA_ENGINE.md`) يجب أن يعمل عبر طابور مهام (Queue) قابل لزيادة عدد العمّال (Workers) أفقيًا دون تغيير الكود.
- قاعدة البيانات مصممة لتحمّل ملايين السجلات في جداول Analytics/Snapshots (فهرسة، تقسيم منطقي حسب التاريخ عند الحاجة لاحقًا).
- المعمارية Multi-Provider تسمح بإضافة مزود بيانات جديد بإضافة موديول واحد فقط دون تعديل الكود الأساسي.

## الموثوقية والتوفر (Reliability & Availability)

- هدف توفر أولي: 99% شهريًا (MVP)، يرتفع إلى 99.9% بعد استقرار المنتج.
- فشل استدعاء مزود بيانات خارجي يجب ألا يُسقط الطلب كاملاً؛ يُعرض ما توفر من بيانات مع رسالة واضحة عن الجزء غير المتاح، وإعادة محاولة تلقائية محدودة (Retry with backoff).
- كل عملية كتابة حساسة (تقديم طلب وكالة، تغيير اشتراك) يجب أن تكون Idempotent لمنع التكرار عند إعادة الإرسال.

## الأمان (Security)

راجع `17_SECURITY.md` للتفاصيل الكاملة. ملخص إلزامي:

- تشفير كلمات المرور (bcrypt/argon2)، عدم تخزين أي سر بنص صريح.
- HTTPS إلزامي في كل البيئات فوق Local.
- حماية من حقن SQL (عبر Prisma ORM حصرًا، لا استعلامات خام غير محمية)، XSS، CSRF.
- Rate limiting على كل Endpoint عام، وخصوصًا توليد التقارير (منع إساءة الاستخدام/Scraping مضاد).
- بيانات المتقدمين للوكالة (هاتف، بريد، Telegram) مشفّرة أثناء التخزين إن أمكن على مستوى الحقل، ووصول محدود بالأدوار (RBAC).

## قابلية الصيانة (Maintainability)

- الكود منظم بمعمارية طبقات واضحة (`05_SYSTEM_ARCHITECTURE.md`): لا منطق أعمال داخل مكونات الواجهة مباشرة.
- كل موديول (Provider, AI Engine, CRM, Auth) مستقل قدر الإمكان (Loose coupling) وقابل للاختبار منفردًا.
- توثيق inline (TSDoc/JSDoc) لأي دالة تحسب Score أو منطق أعمال غير بديهي.
- ملفات لا تتجاوز ~300–400 سطر كقاعدة عامة؛ عند التجاوز يُقسَّم الملف.

## قابلية الاستخدام (Usability)

- **العربية (RTL) هي اللغة الافتراضية والأساسية** منذ أول شاشة، وليست إضافة لاحقة. الإنجليزية (LTR) لغة ثانوية عبر مبدّل لغة كامل (i18n حقيقي، لا ترجمة سطحية). التفاصيل الكاملة في `16_UI_UX.md`.
- الواجهة يجب أن تُفهم النتيجة الأساسية (Score) خلال أول 3 ثوانٍ من النظر للصفحة (Above the fold).
- كل رقم/مؤشر تقديري يحمل Tooltip أو وسم "تقديري" مرئي بدون الحاجة للنقر.
- جودة التصميم البصري (خصوصًا صفحة الهبوط) يجب أن تطابق معيار المنصات العالمية المذكور في `16_UI_UX.md` — لا يُقبل تصميم "وظيفي بس" دون مستوى بصري احترافي.

## قابلية النقل والتوسع التقني (Portability)

- بيئة التطوير بالكامل عبر Docker/Docker Compose، بحيث يعمل أي مطور بنفس الإعداد.
- لا اعتماد على خدمة سحابية واحدة بشكل غير قابل للفك (Vendor lock-in) في الطبقات الأساسية (DB، Queue، Storage) — استخدام معايير مفتوحة (PostgreSQL، Redis، S3-compatible storage).
- المشروع يُبنى ويُشغَّل عبر سيرفر Linux (Ubuntu) عبر opencode CLI — لا اعتماد على أدوات أو مسارات خاصة بنظام تشغيل معيّن (`18_DEPLOYMENT.md`).

## الملاحظة والمراقبة (Observability)

- تسجيل (Logging) منظم (Structured JSON logs) لكل خطأ وكل عملية جمع بيانات فاشلة.
- سجل عمليات (Audit Log) لكل إجراء إداري حساس (`14_ADMIN_PANEL.md`).
- تنبيهات أساسية عند ارتفاع نسبة فشل جمع البيانات فوق عتبة معينة.

## الامتثال والقيود القانونية

- عدم استخدام بيانات مسربة، وعدم انتحال صفة TikTok الرسمية.
- سياسة خصوصية وشروط استخدام واضحتين قبل أي إطلاق عام (`17_SECURITY.md`).
- الامتثال لـ GDPR-like principles كحد أدنى: حق المستخدم في طلب حذف بياناته.
