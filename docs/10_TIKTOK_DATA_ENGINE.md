# 10 — Data Provider Engine (TikTok + Multi-Provider)

مسؤولية هذا الموديول: جمع بيانات خام من مصادر خارجية وتخزينها كـ `AccountSnapshot` نظيف وموحّد الصيغة، بغض النظر عن المصدر. لا يحسب هذا الموديول أي Score — ذلك مسؤولية `09_AI_ANALYSIS_ENGINE.md`.

## واجهة موحّدة (Provider Interface)

كل مزود بيانات يطبّق نفس الواجهة، حتى لو اختلفت طريقة الجلب داخليًا:

```ts
interface DataProvider {
  key: "tiktok" | "instagram" | "youtube" | "kick" | "twitch";
  fetchProfile(username: string): Promise<RawProfileData>;
  fetchRecentContent(username: string, limit: number): Promise<RawContentItem[]>;
  fetchLiveStatus?(username: string): Promise<RawLiveStatus | null>; // اختياري، ليس كل مزود يدعمه
}
```

المرحلة الأولى (MVP) تُنفّذ `TikTokProvider` فقط. باقي المزودين (`InstagramProvider`, `YouTubeProvider`, `KickProvider`, `TwitchProvider`) خارج نطاق MVP (`01_PROJECT_OVERVIEW.md`)، لكن الواجهة يجب أن تُبنى بحيث إضافتهم لاحقًا = إضافة Class جديد يطبّق `DataProvider`، بدون تعديل أي كود في API Layer أو AI Engine.

## TikTokProvider — مصادر البيانات المسموحة

**إلزامي**: الاعتماد حصرًا على وسائل وصول للبيانات العامة ضمن حدود مشروعة (Public profile pages / رسمية إن توفرت لاحقًا)، وعدم استخدام أي بيانات مسربة أو قواعد بيانات مخترقة تحت أي ظرف (`README.md`, `02_BUSINESS_REQUIREMENTS.md`). الطريقة التقنية الدقيقة للجلب (headless browser / رسمي إن توفر لاحقًا) تُحدَّد وتُختبر عمليًا في مرحلة `phase_03` من التنفيذ، مع مراعاة:

- احترام حدود معدل الطلبات لتفادي الحظر (Throttling داخلي، ليس فقط حماية من إساءة استخدام مستخدمينا).
- تخزين نتيجة كل طلب كـ Snapshot، لتقليل الحاجة لإعادة الجلب لنفس الحساب خلال فترة قصيرة (Cache-first).
- التعامل مع فشل/حظر مؤقت بأناقة: إعادة محاولة محدودة (Retry with exponential backoff)، ثم فشل واضح للمستخدم (برسالة عربية) بدل تعليق غير محدود.

## الحقول الخام المُجلَبة فعليًا (Provider Layer)

هذه فقط — الباقي في `03_FUNCTIONAL_REQUIREMENTS.md` مشتق لاحقًا وليس مجلوبًا مباشرة:

- صورة الحساب، الاسم، Username، حالة التوثيق، نوع الحساب (إن كان ظاهرًا)، الوصف/Bio.
- عدد المتابعين، عدد المتابَعين، إجمالي الإعجابات، عدد الفيديوهات.
- قائمة آخر N فيديو (افتراضي N=20): المشاهدات، اللايكات، التعليقات، المشاركات، تاريخ النشر، المدة، الوصف/الهاشتاقات لكل فيديو.
- حالة البث المباشر الحالية إن أمكن رصدها وقت الطلب.

## الحقول المشتقة داخل هذا الموديول (Derivation، ليست AI بعد)

هذه عمليات معالجة أولية بسيطة (وليست Scoring) تحدث هنا قبل تمرير البيانات لـ AI Engine:

- `avgViews/avgLikes/avgComments/avgShares` = متوسط بسيط على العينة المجلوبة.
- `bioLanguageGuess` = كشف لغة (Language detection) بسيط على نص الـ Bio والكابشنز.
- تجميع أوقات النشر لكل فيديو مُجلَب (لاستخدامها لاحقًا في "أفضل أوقات النشر" الفعلية، لا التقديرية).

الحقول **التقديرية الثقيلة** (الدولة، تاريخ الإنشاء، كل الـ Scores) تُحسب حصرًا في `09_AI_ANALYSIS_ENGINE.md`، لا هنا — فصل الاهتمامات إلزامي (`05_SYSTEM_ARCHITECTURE.md` مبدأ 3).

## معالجة البث المباشر (LIVE)

TikTok لا يوفر سجلاً تاريخيًا علنيًا لكل بثوث حساب. لذلك:

- إن أمكن رصد بث نشط وقت الطلب → يُسجَّل `LiveSession` بـ `isEstimated: false`.
- عدد مرات البث خلال آخر شهر ومتوسط المدة → **تقديريان** (`isEstimated: true`)، يُشتقان من أي إشارات غير مباشرة متاحة (مثال: منشورات/تفاعلات مرتبطة بجلسات بث سابقة إن وُجدت)، أو يُعرضان كـ "غير كافٍ للتقدير" إن لم تتوفر إشارات كافية بدل رقم مختلَق.

## طابور المعالجة (Queue Flow)

1. طلب تحليل جديد → `AnalyzeAccountJob` يُضاف لـ BullMQ.
2. Worker يستدعي `provider.fetchProfile()` ثم `provider.fetchRecentContent()`.
3. عند النجاح → يُنشأ `AccountSnapshot` → يُطلق Job تالٍ `GenerateAnalysisReportJob` (يستدعي AI Engine).
4. عند الفشل → إعادة محاولة (حتى 3 مرات، Backoff أسّي) → إن استمر الفشل، الحالة تُحدَّث إلى `failed` مع سبب واضح بالعربية يُعرض للمستخدم.

## التخزين المؤقت (Cache Policy)

- Snapshot أحدث من X ساعة (افتراضي مقترح: 6 ساعات، قابل للتعديل من Admin) يُستخدم مباشرة دون إعادة جلب.
- طلب "تحديث فوري" (Force refresh) متاح فقط للخطط المدفوعة، لمنع إساءة استخدام حد الطلبات على المصدر الخارجي.

## حدود صارمة

- ممنوع الزحف (Scraping) بمعدل يعرّض المنصة لحظر جماعي — يجب وجود Throttling مركزي على مستوى كل الـ Workers، لا لكل طلب منفرد فقط.
- ممنوع تخزين بيانات شخصية حساسة غير ضرورية من البروفايل العام (مثال: أرقام هواتف ظاهرة في Bio تُعامل بحذر، لا تُستخدم تسويقيًا دون سياق).
- كل تغيير مستقبلي في طريقة الجلب (مثال: التحوّل لـ API رسمي إن أتيح) يجب ألا يغيّر `DataProvider` interface — فقط التنفيذ الداخلي لـ `TikTokProvider`.
