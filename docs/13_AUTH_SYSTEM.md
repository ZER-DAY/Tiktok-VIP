# 13 — Auth System

المكتبة: Better Auth (`06_TECH_STACK.md`). هذه الوثيقة تحدد سلوك المصادقة والصلاحيات (RBAC) الملزم.

## طرق تسجيل الدخول

- بريد إلكتروني + كلمة مرور (Hash عبر argon2/bcrypt، لا نص صريح — `17_SECURITY.md`).
- OAuth: Google كحد أدنى للـ MVP. البنية تسمح بإضافة مزودين آخرين (Apple, Telegram Login نظرًا لطبيعة الجمهور) بإضافة Provider في إعدادات Better Auth فقط.

## الجلسات (Sessions)

- جلسة عبر Cookie آمن (`httpOnly`, `secure`, `sameSite=lax`).
- مدة الجلسة الافتراضية: 30 يومًا مع تجديد تلقائي عند النشاط (Sliding expiration).
- تسجيل خروج يُبطل الجلسة فورًا من الخادم (لا الاكتفاء بحذف الكوكي من العميل).

## الاستخدام بدون تسجيل دخول (Guest Flow)

يسمح للزائر بتوليد تقرير تحليل واحد دون حساب (`03_FUNCTIONAL_REQUIREMENTS.md` FR-3)، مربوط بـ Rate limit على IP/Fingerprint (وليس على مستخدم). حفظ التقرير وتتبعه لاحقًا يتطلب إنشاء حساب — عند إنشاء الحساب مباشرة بعد تحليل ضيف، يُربط آخر تقرير ضيف بالحساب الجديد تلقائيًا (تجربة سلسة، لا فقدان للنتيجة).

## الأدوار (Roles) — القائمة الكاملة

| الدور            | الوصف                                              |
| ---------------- | -------------------------------------------------- |
| `creator`        | مستخدم عادي، دور افتراضي لأي تسجيل جديد            |
| `agency_staff`   | عضو فريق توظيف بالوكالة، وصول لـ CRM محدود         |
| `agency_admin`   | مدير وكالة، وصول كامل لـ CRM وإعداداته             |
| `platform_admin` | مدير المنصة، وصول كامل لكل شيء بما فيه Admin Panel |

مستخدم واحد قد يحمل أكثر من دور (مثال: `platform_admin` يحمل ضمنيًا صلاحيات `agency_admin`، لكن هذا يُنفَّذ صراحة عبر تعيين الأدوار في `UserRole`، لا افتراضًا ضمنيًا في الكود لتفادي ثغرات صلاحيات خفية).

## نموذج الصلاحيات (Permissions)

صلاحيات دقيقة (Granular) وليس أدوارًا فقط، لمرونة أكبر لاحقًا. أمثلة مفاتيح الصلاحيات:

```
report.view_own
report.view_any
crm.view_applicants
crm.edit_applicant_status
crm.view_contact_info
crm.manage_assignees
admin.manage_users
admin.manage_plans
admin.manage_settings
admin.view_audit_logs
```

كل `Role` مرتبط بمجموعة `Permission` عبر `RolePermission` (`07_DATABASE_DESIGN.md`). فحص الصلاحية في الكود يكون دائمًا بمفتاح الصلاحية (`hasPermission(user, "crm.edit_applicant_status")`)، لا بمقارنة اسم الدور مباشرة — هذا يسمح بتعديل من يملك ماذا من `14_ADMIN_PANEL.md` دون تعديل كود.

## Middleware مركزي

طبقة واحدة (`/src/modules/auth/middleware.ts` أو مكافئ) تُطبَّق على كل Route محمي، تتحقق من: (1) وجود جلسة صالحة، (2) الصلاحية المطلوبة لهذا الـ Endpoint تحديدًا. لا يُسمح بفحص صلاحيات يدوي متكرر بمنطق مختلف داخل كل Handler (`05_SYSTEM_ARCHITECTURE.md` مبدأ 6).

## استرجاع كلمة المرور والتحقق من البريد

- رابط استرجاع صالح لمدة 1 ساعة، Token عشوائي آمن (لا يمكن تخمينه)، يُستهلك مرة واحدة فقط.
- تأكيد البريد الإلكتروني عند التسجيل (غير إلزامي لاستخدام الميزات الأساسية، لكن إلزامي قبل تفعيل أي دور CRM/Admin).
- كل رسائل البريد الإلكتروني (تأكيد، استرجاع، إشعارات) بالعربية افتراضيًا حسب `preferredLocale` للمستخدم (`07_DATABASE_DESIGN.md`).

## أمان إضافي إلزامي

- Rate limiting على محاولات تسجيل الدخول (منع Brute force).
- تسجيل كل تسجيل دخول ناجح/فاشل حساس (محاولات متكررة فاشلة) في نظام مراقبة أساسي.
- أي تغيير على دور مستخدم (منح/سحب صلاحية CRM أو Admin) يُسجَّل في `AuditLog` إلزاميًا.
