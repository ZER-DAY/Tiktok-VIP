# 19 — Testing

## فلسفة الاختبار

كل ميزة تُعتبر ناقصة الإنجاز بدون اختبار واحد على الأقل (`03_FUNCTIONAL_REQUIREMENTS.md` — Definition of Done). الأولوية للاختبار على `09_AI_ANALYSIS_ENGINE.md` تحديدًا، لأنه المكوّن الذي تُبنى عليه ثقة المستخدم في المنتج بأكمله.

## أدوات الاختبار

| النوع                        | الأداة                                       |
| ---------------------------- | -------------------------------------------- |
| Unit tests                   | Vitest                                       |
| Integration tests (API + DB) | Vitest + قاعدة بيانات اختبار معزولة (Docker) |
| E2E (واجهة كاملة)            | Playwright                                   |
| Component tests (React)      | React Testing Library                        |

## طبقات الاختبار الإلزامية

### 1. AI Analysis Engine (أولوية قصوى)

- اختبارات وحدة لكل دالة حساب Score بمدخلات ثابتة معروفة النتيجة المتوقعة (مثال: مدخلات تفاعل مرتفع صناعية → Engagement Quality Score يجب أن يقع ضمن نطاق متوقع).
- اختبار توزيع الأوزان عند غياب مكوّن (سيناريو أول تحليل بدون Snapshot سابق — `09_AI_ANALYSIS_ENGINE.md`).
- مجموعة اختبار يدوية (Golden dataset) من ≥30 حسابًا حقيقيًا متنوعة الحجم، مراجعة النتائج يدويًا للتأكد من المنطقية النسبية، تُعاد كلما تغيّرت صيغة الحساب.

### 2. Data Provider Engine

- اختبار `TikTokProvider` ضد بيانات Mock ثابتة (لا استدعاء فعلي في CI لتفادي هشاشة/حظر).
- اختبار سيناريوهات الفشل: Timeout، حظر مؤقت، بيانات ناقصة — التأكد أن النظام يتعامل معها بأناقة (`10_TIKTOK_DATA_ENGINE.md`) لا يتعطل بالكامل.

### 3. API Layer

- اختبار تكامل لكل Endpoint في `08_API_SPECIFICATION.md`: حالة نجاح، حالة تحقق فاشل، حالة صلاحية مرفوضة.
- اختبار RBAC صراحة: مستخدم بدون صلاحية `crm.view_applicants` يجب أن يحصل فعليًا على `403`، ليس فقط إخفاء الزر في الواجهة.

### 4. Frontend/Components

- اختبار مكونات حرجة: بطاقة الـ Score، نموذج تقديم الوكالة، جدول CRM (فلترة/ترتيب).
- اختبار حالات Loading/Empty/Error لصفحة التقرير (`16_UI_UX.md`).
- **اختبار i18n/RTL**: التأكد أن `/` يعرض عربي RTL افتراضيًا، وأن مبدّل اللغة ينقل لـ `/en` LTR دون كسر التخطيط، وأن لا نص Hardcoded ظاهر خارج ملفات الترجمة.

### 5. E2E (المسارات الحرجة فقط)

- مسار كامل: زائر يدخل يوزر → يرى تقريرًا بالعربية → يسجّل حسابًا → يرى نفس التقرير محفوظًا في لوحته.
- مسار كامل: مستخدم مؤهل → يقدّم طلب وكالة → يظهر الطلب في CRM بحالة `new`.
- مسار كامل: موظف CRM → يغيّر حالة طلب ويضيف ملاحظة → السجل يظهر في `ApplicationStatusHistory`.

## معايير القبول للدمج (CI Gate)

لا يُدمج أي Pull Request في `main` إذا: فشل أي اختبار موجود، انخفضت تغطية الاختبار (Coverage) عن الحد الأدنى المتفق عليه لكل موديول جديد (مقترح: 70% لموديولات المنطق الحرج كـ AI Engine)، أو فشل Type check/Lint (`18_DEPLOYMENT.md`).

## اختبار الأداء (Load Testing) — قبل الإطلاق العام فقط

اختبار حمل بسيط على `POST /api/analyze` للتأكد من سلوك Queue تحت ضغط (عشرات الطلبات المتزامنة) قبل أي إطلاق تسويقي واسع، وليس ضروريًا في كل Sprint.
